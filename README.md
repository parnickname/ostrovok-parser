# ostrovok-parser

Парсер и сборщик данных для AI-агента путешествий «О!дин запрос» (трек Островка). Здесь живёт всё, что связано с
данными: загрузчики открытых источников, ручные правки, реестр источников, сборка и проверка снапшота. Результат —
папка `data/snapshot/` в формате [docs/snapshot-format.md](docs/snapshot-format.md); бэкенд читает её при старте.

Это отдельный сервис-конвейер, а не работающий сервер: он ничего не отдаёт по сети, а собирает файлы. Данные лежат
файлами, а не в PostgreSQL (решение основного проекта: снапшот только для чтения, меняется вместе с релизом).

## Что здесь

```
data/
  requirements.txt     зависимости загрузчиков с версиями (сейчас только requests)
  loaders/<источник>/  скрипты загрузки, по каталогу на источник; результат — out/<набор>.jsonl
  overrides/           ручные правки поверх источников (visa.csv и т. п.)
  reports/             отчёты сверки источников (например, visa-diff.md)
  sources.yaml         реестр источников: и взятых, и рассмотренных
  build.py             собирает snapshot/ из loaders/ и overrides/
  refresh.py           перезагружает источники, собирает и проверяет снапшот (запускается по расписанию)
  validate.py          проверяет snapshot/ по схемам из CFC-3
  snapshot/            manifest.json и <набор>.jsonl — то, что читает бэкенд
docs/
  data.md              задачи P1-DS-01…08 с подзадачами и распределением по людям
  data-phase2.md       задачи P2-DS-01…03 (фаза 2) и их распределение
  data-phase3.md       задачи P3-DS-01…03 (фаза 3, набор eval) и их распределение
  snapshot-format.md   контракт формата снапшота (CFC-3, CFC-5, статусы виз)
eval/cases/                  диалоги для проверки памяти (P2-DS-03.1), формат — eval/README.md
scripts/check-changelog.py   проверка CHANGELOG.md
.github/workflows/ci.yml     проверки: validate.py и changelog
.github/workflows/refresh.yml  регулярная пересборка: раз в неделю и раз в месяц, результат — pull request
```

## Быстрый старт

Нужны Python 3.12 и `requests` (версия закреплена в `data/requirements.txt`).

```bash
python3 -m pip install -r data/requirements.txt
python3 data/build.py && python3 data/validate.py     # на Windows: python
```

Сборка детерминирована: без изменений входных данных `sha256` наборов и `built_at` в `manifest.json` не меняются. Файлы в `snapshot/` всегда с переводами строк LF (`data/.gitattributes`), иначе `sha256` разойдётся.

## Что на выходе

Одиннадцать наборов JSON Lines и манифест: `countries`, `visa`, `cities`, `airports`, `stations`, `destinations`,
`climate`, `hotels`, `routes`, `rail_routes`, `calibration`. Поля, типы и правила — в
[docs/snapshot-format.md](docs/snapshot-format.md). Для каждого набора обязательно: схема из CFC-3, стабильный `id`
(от него бэкенд считает seed синтетических цен, поэтому `id` не меняется между пересборками), `sources` с именами из
`data/sources.yaml`, запись в `manifest.json`, и `python3 data/validate.py` проходит.

## Как бэкенд принимает снапшот

Бэкенд (репозиторий основного проекта, пакет `internal/dataset`) не стартует, если:

- нет любого из одиннадцати наборов в манифесте или файла на диске;
- не совпали `records` или `sha256`;
- в записи есть неизвестное поле или сломана ссылка между наборами (город → аэропорт и вокзал, направление → город и
  страна, отель → направление, маршрут → аэропорты и вокзалы);
- у направления нет ни аэропорта, ни вокзала;
- в `calibration` нет 12 значений `season_factor`, цены `bed_price_rub` для 2–5 звёзд или `country_price_level` для
  страны любого направления;
- имя в `sources` не является провайдером со статусом `used` в `sources.yaml` снапшота.

Копию `sources.yaml` бэкенд ждёт внутри папки снапшота. Передавать ему нужно всю папку `data/snapshot/`.

## Решения команды

Приняты 2026-10-26. Действуют для обоих исполнителей; если решение расходится с `docs/data.md`, это вопрос команде.

| Вопрос | Решение |
|---|---|
| Q-006, размер каталога | 30–40 направлений, не меньше трети зарубежных, не меньше пяти визовых для паспорта РФ |
| Q-007, города отправления в СНГ | Беларусь, Казахстан, Узбекистан, Армения. Остальные страны СНГ пока исключены |
| Город отправления | Город, у которого `airports[]` или `stations[]` не пуст; отдельного списка нет. Критерий `04.2` «у каждого города отправления есть аэропорт» проверяется так: город без аэропорта лишился его не из-за ошибки привязки, а потому что в OurAirports нет рейсов. Вокзалы только по России (`06.2`), поэтому в BY, KZ, UZ, AM отправление возможно только из городов с аэропортом |
| Каталог и визы | `03.1` не ждёт `02`. Страны каталога выбираются по общему знанию, визовых для паспорта РФ берётся с запасом (7–8, нужно не меньше пяти). Статус визы в `destinations` не записывается, он есть только в `visa.jsonl`. В `02.4` Саня сверяет визовые данные по странам каталога со справкой МИД и правит их в `overrides/visa.csv`; состав каталога он не меняет. Когда `02.2` смержена, Parnick пересчитывает визовые страны паспорта РФ в каталоге и, если их меньше пяти, правит `03.1` отдельным коммитом |
| Сборка `calibration` | Это один объект, а `07` разделена между исполнителями: каждый загрузчик пишет свою часть — отдельный объект в своём `out/calibration.jsonl` (например, `{"fx_rub": {...}, "sources": ["cbr"]}`), `build.py` склеивает части в один объект. Ключи верхнего уровня у частей не должны пересекаться (иначе сборка падает с именами загрузчиков), `sources` объединяются |
| Q-009, источник блоков `early_checkin` и `date_change` | Правил больших сетей, на которые можно сослаться, нет: Marriott и Hilton оставляют время и цену раннего заезда отелю, цифр в открытом виде нет. Источник — закон: постановление Правительства РФ № 1912 от 27.11.2025, действует с 01.03.2026 по 01.03.2032 (реестр: `rf-hotel-rules`). Что он даёт: заезд раньше времени заезда — не больше платы за половину суток, и только за срок до 12 часов (п. 33), поэтому `price_share` = 0,5; отказ от брони до дня заезда — возврат полностью, позже или незаезд — не больше платы за сутки (п. 16), поэтому смена дат до дня заезда бесплатна. Чего закон не даёт, то остаётся значением CFC-10 и записывается с источником `synthetic` рядом с `rf-hotel-rules`: `earliest` = `10:00` и сбор за невозвратный тариф 0,2. Подробности — в [docs/data-phase2.md](docs/data-phase2.md#как-посчитан-date_change-q-009) |
| Вокзалы в `destinations` | В `03.1` у направлений `stations: []`. Вокзалы делает Саня в `06.2`, после чего заполняет `stations[]` у российских направлений в том же PR |
| `cities.airports[]` и `airports.city_id` | Порядок: `cities` с `airports: []`, затем `airports`, затем заполнение `cities.airports[]`. Заполнение входит в `04.2` |

## Как работаем

- Ветки: `main` и по одной личной ветке у каждого. В `main` — только через pull request.
- Подзадача выполнена, когда её PR смержен в `main`. Зависимость внутри роли блокирующая: подзадачу не начинают, пока
  зависимость не смержена.
- Мерж — только «Create a merge commit». Squash и rebase меняют хеши, и записи журнала изменений станут ложными.
  Свежий `main` в личную ветку подтягиваем мержем, не rebase.
- Не добавляем в подзадачу ничего, чего нет в её колонках «Что» и «Готово, когда». Неясность или противоречие в
  `docs/data.md` — вопрос команде, а не догадка.
- Контракт формата меняется только через спеку основного проекта, а не договорённостью в чате.

### Журнал изменений

Каждое изменение записывается в [CHANGELOG.md](CHANGELOG.md) строго по
[Keep a Changelog 1.1.0](https://keepachangelog.com/ru/1.1.0/): раздел `[Unreleased]`, разделы «Добавлено», «Изменено»,
«Устарело», «Удалено», «Исправлено», «Безопасность» (в таком порядке). В каждом пункте — суть, затем «Технически:» с
деталями и короткий хеш коммита в обратных кавычках, например (`8daade7`). Коммит не может содержать свой хеш, поэтому
порядок такой: коммит с работой, затем отдельный коммит `docs(changelog): …` с записью и хешем первого. Проверка:
`python3 scripts/check-changelog.py CHANGELOG.md`; в CI она идёт на каждом PR.

## Регулярная пересборка

Источники меняются, а снапшот без нашего участия — нет, поэтому `data/refresh.py` перезагружает их по расписанию
(`.github/workflows/refresh.yml`):

| Группа | Когда | Что |
|---|---|---|
| `weekly` | по понедельникам | визовая матрица, вокзалы и расписания поездов, прямые рейсы и цены на билеты (Travelpayouts), курсы ЦБ |
| `monthly` | первого числа месяца | всё, что загружается из сети: города, аэропорты, вокзалы, отели, климат, статистика Росстата и Всемирного банка |

```bash
python3 data/refresh.py --group weekly      # или monthly, all; --dry-run только печатает шаги
```

Скрипт запускает загрузчики в порядке зависимостей, затем `build.py` и `validate.py`, а если наборы изменились, ставит
свежий `fetched_at` у перезагруженных источников в `sources.yaml`. Без изменений в источниках в git ничего не меняется
(`built_at` в манифесте тоже). Шаг, которому нужен ключ или токен, пропускается, если секрета нет. Рабочий процесс
открывает pull request в `main`, мержит человек; бэкенд получает новый снапшот так же, как раньше, с релизом.

Что нужно один раз настроить в репозитории: в Settings → Actions → General права «Read and write» и «Allow GitHub
Actions to create and approve pull requests», в Settings → Secrets → Actions секреты `YANDEX_RASP_API_KEY` и
`TRAVELPAYOUTS_TOKEN`. Вручную рабочий процесс запускается из вкладки Actions («Run workflow»).

## Ключи и секреты

Ключи API (Яндекс Расписания для `06.2`–`06.3`, токен Travelpayouts для `07.3` и `06.4`) читаются из переменных
окружения (`YANDEX_RASP_API_KEY`, `TRAVELPAYOUTS_TOKEN`) или из файла `.env` и никогда не попадают в git: `.env` в
`.gitignore`. Токен Travelpayouts: регистрация на https://www.travelpayouts.com бесплатная, токен — в личном кабинете (профиль, раздел API).

## Простое и временное

Упрощения в коде помечаются комментариями `impulse: <потолок>, <когда убирать>`. Пример — разбор `sources.yaml` по
строкам в `data/validate.py`.
