# ostrovok-parser

Парсер и сборщик данных для AI-агента путешествий «О!дин запрос» (трек Островка). Здесь живёт всё, что связано с
данными: загрузчики открытых источников, ручные правки, реестр источников, сборка и проверка снапшота. Результат —
папка `data/snapshot/` в формате [docs/snapshot-format.md](docs/snapshot-format.md); бэкенд читает её при старте.

Это отдельный сервис-конвейер, а не работающий сервер: он ничего не отдаёт по сети, а собирает файлы. Данные лежат
файлами, а не в PostgreSQL (решение основного проекта: снапшот только для чтения, меняется вместе с релизом).

## Что здесь

```
data/
  requirements.txt     зависимости загрузчиков с версиями (сейчас только requests)
  loaders/<источник>/  скрипты загрузки, по каталогу на источник; результат — out/<набор>.jsonl
  overrides/           ручные правки поверх источников (visa.csv и т. п.)
  reports/             отчёты сверки источников (например, visa-diff.md)
  sources.yaml         реестр источников: и взятых, и рассмотренных
  build.py             собирает snapshot/ из loaders/ и overrides/
  validate.py          проверяет snapshot/ по схемам из CFC-3
  snapshot/            manifest.json и <набор>.jsonl — то, что читает бэкенд
docs/
  data.md              задачи P1-DS-01…08 с подзадачами и распределением по людям
  snapshot-format.md   контракт формата снапшота (CFC-3, CFC-5, статусы виз)
scripts/check-changelog.py   проверка CHANGELOG.md
.github/workflows/ci.yml     проверки: validate.py и changelog
```

## Быстрый старт

Нужны Python 3.12 и `requests` (версия закреплена в `data/requirements.txt`).

```bash
python3 -m pip install -r data/requirements.txt
python3 data/build.py && python3 data/validate.py     # на Windows: python
```

Сборка детерминирована: без изменений входных данных `sha256` наборов в `manifest.json` не меняется, меняется только
`built_at`. Файлы в `snapshot/` всегда с переводами строк LF (`data/.gitattributes`), иначе `sha256` разойдётся.

## Что на выходе

Одиннадцать наборов JSON Lines и манифест: `countries`, `visa`, `cities`, `airports`, `stations`, `destinations`,
`climate`, `hotels`, `routes`, `rail_routes`, `calibration`. Поля, типы и правила — в
[docs/snapshot-format.md](docs/snapshot-format.md). Для каждого набора обязательно: схема из CFC-3, стабильный `id`
(от него бэкенд считает seed синтетических цен, поэтому `id` не меняется между пересборками), `sources` с именами из
`data/sources.yaml`, запись в `manifest.json`, и `python3 data/validate.py` проходит.

## Как бэкенд принимает снапшот

Бэкенд (репозиторий основного проекта, пакет `internal/dataset`) не стартует, если:

- нет любого из одиннадцати наборов в манифесте или файла на диске;
- не совпали `records` или `sha256`;
- в записи есть неизвестное поле или сломана ссылка между наборами (город → аэропорт и вокзал, направление → город и
  страна, отель → направление, маршрут → аэропорты и вокзалы);
- у направления нет ни аэропорта, ни вокзала;
- в `calibration` нет 12 значений `season_factor`, цены `bed_price_rub` для 2–5 звёзд или `country_price_level` для
  страны любого направления;
- имя в `sources` не является провайдером со статусом `used` в `sources.yaml` снапшота.

Копию `sources.yaml` бэкенд ждёт внутри папки снапшота. Передавать ему нужно всю папку `data/snapshot/`.

Известное расхождение, перенесённое как есть: по описанию (CFC-3) `build.py` кладёт копию `sources.yaml` в `snapshot/`, но
в коде этого шага пока нет. Это нужно решить до передачи снапшота бэкенду.

## Как работаем

- Ветки: `main` и по одной личной ветке у каждого. В `main` — только через pull request.
- Подзадача выполнена, когда её PR смержен в `main`. Зависимость внутри роли блокирующая: подзадачу не начинают, пока
  зависимость не смержена.
- Мерж — только «Create a merge commit». Squash и rebase меняют хеши, и записи журнала изменений станут ложными.
  Свежий `main` в личную ветку подтягиваем мержем, не rebase.
- Не добавляем в подзадачу ничего, чего нет в её колонках «Что» и «Готово, когда». Неясность или противоречие в
  `docs/data.md` — вопрос команде, а не догадка.
- Контракт формата меняется только через спеку основного проекта, а не договорённостью в чате.

### Журнал изменений

Каждое изменение записывается в [CHANGELOG.md](CHANGELOG.md) строго по
[Keep a Changelog 1.1.0](https://keepachangelog.com/ru/1.1.0/): раздел `[Unreleased]`, разделы «Добавлено», «Изменено»,
«Устарело», «Удалено», «Исправлено», «Безопасность» (в таком порядке). В каждом пункте — суть, затем «Технически:» с
деталями и короткий хеш коммита в обратных кавычках, например (`8daade7`). Коммит не может содержать свой хеш, поэтому
порядок такой: коммит с работой, затем отдельный коммит `docs(changelog): …` с записью и хешем первого. Проверка:
`python3 scripts/check-changelog.py CHANGELOG.md`; в CI она идёт на каждом PR.

## Ключи и секреты

Ключи API (Яндекс Расписания для `06.2`–`06.3`, токен Travelpayouts для `07.3`) читаются из переменных окружения и
никогда не попадают в git: `.env` в `.gitignore`.

## Простое и временное

Упрощения в коде помечаются комментариями `impulse: <потолок>, <когда убирать>`. Пример — разбор `sources.yaml` по
строкам в `data/validate.py`.
